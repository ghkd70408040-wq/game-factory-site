  2. 접수 결과 = 표 한 장: 대상 부품 id(매니페스트) · 계층 T1~T5 · 바뀌는 것(컴포넌트/인스턴스/변주/상태/슬롯/층) · 판정(code/asset/variant/발주) · 시각 변화 여부 · 관문 등급(quick/full/merge) · 산출물. 이 표를 먼저 보이고 시작한다. 표를 채운 뒤 python tools/intake/intake-record.py --request "<문장>" --frame <id|none> --tier T? --change "<층/슬롯/변주/상태>" --verdict <code|asset|variant|발주> --visual <yes|no> --gate <quick|full|merge> --out scratchpad/intake/CURRENT.json 로 기록한다(24시간 유효, 현재 표는 --show). 이 파일이 없거나 낡으면 정본 편집이 Edit/Write·Bash 양쪽에서 exit 2 다.

절대 규칙 (규격 §6 요약)#

  • 파일 하나 = 프레임 하나. 층 순서 Shape→Fill→Stroke→Effect→Slot 고정(채움이 선보다 먼저), Slot은 절대 굽지 않는다. 매니페스트 필드명은 schema.v2.json 이름 그대로(shape.mask·shape.cap_px·slot_safe·baked_layers·bbox.pct).
  • 값은 토큰(Variables/Mode)에서만. 원시값 직접 사용 금지(css-primitives.py·manifest-validate.py가 막는다).
  • 프레임마다 교체점 하나(hook + scope). 옛 것은 은퇴, 부활 금지.
  • 시안이 기준, 재추적 금지, "수치가 눈을 못 이긴다".
  • 부르지 않은 부품 금지. 승인 전 푸시 금지(규격 §6-8) — 게임 HTML·catalog/·board/·*.css 를 바꾼 커밋은 메시지 트레일러 Approval: 이 없으면 tools/hooks/pre-push-approval.py 가 exit 1 로 거부한다. 값은 셋뿐:
    • Approval: pixel-0 — 외형 무변(shot-harness.py 19컷 diff 0 증명)
    • Approval: user-YYYY-MM-DD — 시각 변경(판정판 한 장 → 사용자 "됐다")
    • Approval: tooling — 빌드 스탬프·워크플로·sw.js 키 등 비시각

사용자가 "고치고 푸시해"라고 해도 시각 변경은 비교 이미지 한 장을 먼저 보내고 "됐다"를 받은 뒤 푸시한다. 지시는 승인을 대신하지 않는다. 외형 무변(pixel-0)만 지시만으로 바로 푸시.

  • 판정 산출(§6-9) 형식 하나: 화면당 [조립 실캡처 | 시안 | 부품 | 초점 한 줄], 도장은 사용자만(판정판). 위임 산출(§6-12)은 보고 1(표)+비교 이미지 1+커밋 해시 — 이름이 겹치지 않게 구분한다.
  • 공유 값·자산을 바꾸면 소비처 전량 재확인. 한 에셋 = 한 레시피.
  • 위임 산출물 = 보고 1(표) + 비교 이미지 1 + 커밋 해시. 기록은 scratchpad. 기준 캡처는 --baseline-cache 재사용. 관문 등급대로만 검증.
  • 편집 전 tools/lock.py claim, 끝나면 release. 파이썬·정규식은 Write로 .py 파일을 만들어 실행(히어독 금지). Bash 로도 정본은 못 바꾼다 — >·>>·sed -i·tee·cp/mv/rm·python <정본 경로>·git checkout -- 가 정본 경로를 향하면 tools/hooks/guard-bash-writes.py 가 잠금 + 접수 표를 검사해 exit 2 로 막는다. 읽기는 통과한다.

  4. 시안 유무 — 있으면 S#(규격 §5 S2 tools/intake/sian-intake.py). 없는 "이거 바꿔줘"의 기준은 셋: 현행 배포본 실측(overlay-cap.py 캡처) + 매니페스트 값 + 사용자 지적 문장. 이 셋으로 바뀌는 층만 특정한다(검증1 H2). 수정 요청은 S# 없이도 A0를 연다(검증3 M4).
  5. 시각 변화 여부 · 푸시 지시 해석 — true / false 로 적는다(「있음/없음」이 아니다). true = 관문 full + 승인 필요 + 트레일러 user-YYYY-MM-DD. false = quick + tooling. 사용자가 "고치고 푸시해"라고 해도 시각 변경은 비교 이미지 한 장을 먼저 보내고 "됐다"를 받은 뒤 푸시한다 — 지시는 승인을 대신하지 않는다. 외형 무변(19컷 pixel-0)만 지시만으로 바로 푸시(규격 §6-8 · 검증3 M2).
  6. 소비처(consumers) — 이 부품을 쓰는 화면 전량. 공유 값·자산이면 전량 재확인이 관문 범위다(규격 §6-10).
  7. 통합 — variant / instance / component 중 하나. 「같게·통일·합쳐」 요청일 때 규격 §0-7 통합 판단을 여기에 적는다. 이 칸은 칸 2~3단계의 §4 판정 칸이 아니다 — 부품 자체가 규칙 기하(판·캡슐·버튼·링·광택·겉선)면 판정은 언제나 code 이고, 「저쪽 버튼의 변주냐 인스턴스냐」는 판정 칸이 아니라 이 칸에 적는다. 해당 없으면 해당 없음.

2~3 판정과 방법#

  • 규격 §4: 규칙 기하(판·캡슐·막대·링·광택·접지·외곽선) = code · 조각·손그림·캐릭터·삽화 = asset(발주) · 같은 원형에서 Fill·Effect·State만 다름 = variant · 애매 = ambiguous(둘 다 준비, 관문에서 지는 쪽 폐기). 「저쪽 것과 같게 만들라」는 요청은 그 자체로 variant 판정이 아니다 — 부품이 규칙 기하면 판정은 code, 통합 방식은 접수 표 통합 칸이다.
  • 이미지판이면 규격 §4.1 원칙 0이 먼저다: 그 부품의 Component 정의(Shape·Stroke·Fill·Effect·slot_safe·State·Variant)가 매니페스트에 이미 있는가. 없으면 그것을 만드는 것이 첫 작업이고, 이미지는 그 Component의 Fill/Effect 층 한 구현일 뿐이다. shape.mask 없는 이미지판에 코드 층 = 🔴 차단(규격 §4.1-1).
  • 진입 단계(스킬 asset-frame A0~A12): 값 = theme 토큰만(규격 §2) · 형태 = A1 · 크기·위치 = A2 · 효과 = A5 · 슬롯 = A7 · 변주·상태 = A8 · 배선 = A10. 에셋 1개면 /asset-frame, 발주면 python tools/order/make-order.py --gaps <gaps.json>. 층은 규격 §0 순서로 따로 만들고 재질 값은 규격 §3 재질 시험판 확정본에서만 가져온다.
